01 — turnip_builder.sh — 153 lignes — LU INTÉGRALEMENT
Rôle : télécharger NDK et Mesa, compiler Turnip Android ARM64/KGSL, changer le SONAME et produire un ZIP pour un chargeur compatible Adreno Tools.
L1 : demande bash -e par le shebang. PROBLÈME CERTAIN : la commande documentée « bash ./turnip_builder.sh » ignore cette option du shebang. Aucun « set -e » interne. Dans ce mode, un échec de téléchargement, changement de répertoire, Meson, Ninja, copie ou patchelf peut être suivi d’autres commandes. L’arrêt immédiat n’est assuré que lorsque -e est effectivement activé (invocation adéquate).
L3-5 : couleurs ANSI ; sans conséquence sur le pilote.
L6 : liste des exécutables requis. ccache est utilisé L75-76 sans être testé ; /usr/bin/pkg-config est utilisé L80 sans être testé. La liste exige glslang ET glslangValidator : leur coexistence doit être vérifiée pour la distribution visée ; ne pas présumer qu’un paquet portant un nom fournit les deux commandes.
L7 : répertoire fixé à partir du répertoire courant, pas de celui du script ; fonctionne seulement si l’utilisateur comprend où les fichiers seront créés. Relances dans le même dossier non isolées.
L8-10 : NDK r29, chaîne Linux x86_64, niveau API Android 34. Hôte Linux ARM64 non pris en charge par cette configuration ; README trop général. Le niveau 34 restreint les appareils admissibles au paquet.
L11-12 : téléchargement de Mesa main non figé. La présence de main ne garantit ni la version Vulkan effectivement exposée sur un appareil, ni une compilation durable. Aucun identifiant de commit ni empreinte de source enregistré.
L14 : clear exécuté avant les contrôles ; peut échouer sans TERM/terminfo. Avec -e actif, peut arrêter une exécution non interactive ; sans -e, produit seulement une erreur.
L16-21 : orchestration en quatre étapes ; aucun contrôle explicite de leur résultat par run_all.
L23-37 : teste les commandes puis sort si un manque a été enregistré. deps_missing non initialisé/réinitialisé : une valeur héritée égale à 1 peut provoquer un faux échec. L’absence de commande est bien fatale par exit 1, même sans -e.
L38-39 : installation Mako via pip global, sortie et erreur supprimées. Risque de refus dans un Python géré par la distribution ; pas de venv, ni vérification que pip correspond au Python de Meson. Installer Mako sans version rend aussi la dépendance variable.
L42-44 : mkdir puis cd via $_. Fonctionne en Bash dans ce contexte, mais fragile à une réécriture ; un cd raté n’est pas contrôlé lorsque -e est absent.
L45-48 : téléchargement NDK sans --fail, reprise, empreinte ou journal visible. Un statut HTTP d’erreur peut être enregistré comme ZIP ; unzip masqué. Une seconde extraction peut demander si des fichiers doivent être écrasés.
L49-53 : curl -L suit les redirections de Mesa, mais sans --fail. Extraction masquée et nom mesa-main imposé. Un échec de cd peut laisser la suite travailler au mauvais endroit.
L56-60 : crée des alias cc/c++ vers clang du NDK et modifie PATH globalement.
L61-70 : définit les outils et drapeaux globaux. CFLAGS/CXXFLAGS=-O3 ; LDFLAGS ThinLTO et page maximale 16 Kio. Les variables de compilation croisée ne remplacent pas une configuration native correcte. Une option de lien seule ne prouve pas la compatibilité Android 16 Kio de l’ensemble du paquet et de son chargeur.
L72-87 : fichier Meson pour Android ARM64. ccache nommé comme wrapper (voir nuance B.5). API 34 intégrée aux wrappers Clang. L79 utilise aarch64-linux-android-strip au lieu de llvm-strip utilisé L65 : vérifier cet exécutable dans le NDK r29 ; incohérence à risque à l’étape strip. L80 enferme pkg-config dans un chemin du répertoire bin du NDK, dont aucun contenu .pc n’est préparé par le script. Les dépendances trouvées doivent être examinées dans le log de Meson.
L89-101 : fichier natif : les outils c/cpp/ar/strip/c_ld/cpp_ld sont rangés sous [build_machine], pas sous [binaries]. La sélection explicite des outils natifs n’est donc pas exprimée dans la bonne section. La découverte automatique via PATH peut masquer cette faute. Confirmé par documentation Meson, voir complément B.1.
L103-119 : configuration release, assertions désactivées, LTO thin, Android stub, sans Gallium ni EGL, Turnip freedreno/KGSL et extensions beta. Pas de patch A660, pas de drapeau spécifique Adreno 660. allow-broken-lto n’assure pas le bon fonctionnement de la combinaison. Les options applicatives dépendent du Mesa main téléchargé, absent du ZIP : compatibilité exacte non vérifiée. Le journal redirigé est turnip_workdir/meson_log.
L121 : Ninja écrit ninja_log, sans diffusion console ni contrôle explicite de son code retour.
L123-125 : teste seulement l’existence de la bibliothèque. Une bibliothèque d’une ancienne compilation peut satisfaire ce test malgré un échec courant. Avec -e réellement actif, un échec Meson/Ninja peut arrêter avant le message explicatif L124.
L128-132 : copie la bibliothèque et change le SONAME. Le nom a660_final n’établit aucune optimisation spécifique. Aucun contrôle explicite de cp/patchelf lorsque -e est absent.
L133-145 : génère meta.json. « full LTO » contredit -Db_lto_mode=thin et -flto=thin. « MAX PERF », « tuned for Adreno 660 » et Vulkan 1.4 ne sont pas démontrés. Version du paquet constante 1 ; version du pilote fondée sur la date, sans commit Mesa. Deux builds du même jour sont indiscernables par cette version. minApi=34 cohérent avec la cible déclarée mais non expliqué dans README. Compatibilité du schéma exact à valider avec le chargeur destinataire, qui n’est pas fourni.
L146-150 : zip actualise une archive préexistante ; ne garantit pas un paquet neuf. Test final d’existence seulement : un ancien ZIP peut être annoncé réussi après un échec actuel. Ni zip -T, ni inspection ELF, dépendances dynamiques, alignement après patchelf, ni validation JSON/chargement. La bibliothèque est modifiée après le lien : contrôler le résultat final.
L153 : exécute immédiatement run_all, sans interface d’options.
Verdict : pipeline fragile, reproductibilité absente, promesses de performances et compatibilité non établies. Les cas conditionnels demandent vérification ; ne pas annoncer que tous se produisent systématiquement.

B. Confirmation documentaire et nuances
1. Meson place la sélection des compilateurs/outils sous [binaries]. Le défaut de native.txt L90-96 est confirmé par la référence officielle. Sans fichier natif correct, la découverte via PATH peut faire fonctionner certains environnements et échouer dans d’autres ; ce n’est pas une preuve que Meson échoue forcément sur tous les hôtes.
Source consultée le 09/10/2026 : https://mesonbuild.com/Machine-files.html
2. DÉCOUVERTE SUPPLÉMENTAIRE : strip=true signifie suppression des symboles à l’installation. Le script ne lance que ninja, puis copie directement la bibliothèque de l’arbre de build. Il ne lance ni meson install ni llvm-strip explicitement ; l’option L118 ne garantit donc pas que le .so empaqueté est dépouillé de ses symboles. Ne pas confondre buildtype=release, absence d’informations de debug et suppression de la table des symboles. L’outil erroné L79 est un défaut latent de configuration ; ne pas l’annoncer comme échec certain de Ninja dans le flux présent.
Source : https://mesonbuild.com/Builtin-options.html
3. La documentation NDK indique llvm-strip. Le nom aarch64-linux-android-strip du cross-file est à remplacer par le nom documenté, puis valider le binaire final ; pas d’inspection du ZIP NDK r29 effectuée ici.
Source : https://developer.android.com/ndk/guides/other_build_systems
4. NUANCE pour L6 : la liste officielle actuelle du paquet glslang-tools Ubuntu noble amd64 contient BIEN /usr/bin/glslang ET /usr/bin/glslangValidator. Leur double exigence n’est donc PAS, à elle seule, un bug prouvé sur Ubuntu 24.04 à la date du contrôle. La présence effective du paquet dans le runner reste à vérifier ; d’autres versions/distributions peuvent différer.
Source : https://packages.ubuntu.com/noble/amd64/glslang-tools/filelist
5. NUANCE ccache : les lignes 75-76 le nomment explicitement et le contrôle des dépendances ne le mentionne pas. L’effet de son absence dépend du traitement du wrapper par la version Meson ; ne pas présenter cela comme un blocage certain sans exécution. Le risque de prérequis incomplets concerne surtout l’ensemble des outils et les dépendances du Mesa main effectivement téléchargé.
6. minApi=34 déclare le niveau minimal Android 14 dans les métadonnées. Un support Android plus ancien nécessiterait une nouvelle cible et vérification des API employées ; changer seulement meta.json ne suffit pas.
7. Il manque la source Mesa téléchargée, le NDK et les actions tierces dans cette archive. L’audit ne peut donc pas donner un verdict ligne par ligne sur leurs sources externes, ni garantir Vulkan 1.4, performances A660, compatibilité KGSL/device, schéma du chargeur ou absence de dépendances ELF manquantes.
